Лекция 22. Классический аналитик данных: от сырых данных к проверенному выводу
🎯 Главная идея

Аналитик данных — это не тот, кто «выгружает цифры по запросу». Это тот, кто отвечает на вопрос: «Можно ли верить этим данным, что в них происходит и какое решение из этого следует». Данные — сырьё. SQL — добыча. Проверки качества — фильтр. Статистика — измерительный прибор. ML — телескоп. Рекомендация — результат.

🗄️ Блок 2. Источники данных и событийная модель
⚠️ Главная ловушка новичка: fan-out

В таблице orders один заказ — одна строка. В order_items один заказ может занимать 3 строки (3 товара). Если соединить напрямую — каждый заказ «размножится» на 3 строки, и SUM(amount) утроится. Реальный кейс: менеджер увидел выручку 36 млн ₽ вместо 12 млн ₽ и готовил отчёт для инвесторов. Сначала агрегируем order_items до уровня заказа, потом соединяем.

✅ Tracking plan

Документ, где зафиксировано: какое событие как называется, когда отправляется, какие параметры несёт. Без него purchase, order_paid и success_payment — три «разных» события об одном факте. Реальный кейс: после ребрендинга разработчики переименовали purchase в order_paid, и дашборд конверсии показывал −40% две недели, пока не нашли причину.

-- Выручка по месяцам: сначала правильная гранулярность
SELECT date_trunc('month', created_at) AS month,
       COUNT(DISTINCT order_id)        AS orders,
       SUM(amount)                     AS revenue
FROM orders
WHERE status = 'paid'          -- только оплаченные
GROUP BY 1
ORDER BY 1;
-- Retention M1 через оконную функцию
WITH first_order AS (
  SELECT user_id,
         MIN(date_trunc('month', created_at)) AS cohort
  FROM orders WHERE status = 'paid'
  GROUP BY 1
)
SELECT f.cohort,
       COUNT(DISTINCT f.user_id) AS cohort_size,
       COUNT(DISTINCT o.user_id) AS returned_m1
FROM first_order f
LEFT JOIN orders o
  ON o.user_id = f.user_id
 AND date_trunc('month', o.created_at) = f.cohort + INTERVAL '1 month'
GROUP BY 1;
⚠️ Перед тяжёлым запросом — EXPLAIN

EXPLAIN показывает план: читает ли запрос все партиции, есть ли full scan, какой JOIN выбран. Без него вы не знаете, почему запрос идёт 40 минут. Правило: сначала EXPLAIN, потом запуск.

🕳️ Блок 3а. NULL-семантика и JOIN-типы: скрытые ловушки
🕳️ NULL ≠ NULL

NULL = NULL возвращает NULL, а не TRUE. WHERE col = NULL не находит ничего. Правильно: WHERE col IS NULL. Реальный кейс: фильтр «заказы без промокода» вернул 0 строк, хотя таких было 40%.

🔢 COUNT(*) vs COUNT(col)

COUNT(*) считает строки, COUNT(col) — только не-NULL. Реальный кейс: «10 000 клиентов» по COUNT(*), а с email — 6 200.

🚫 NOT IN с NULL

WHERE id NOT IN (SELECT id FROM t) вернёт пусто, если в подзапросе есть NULL. Используйте NOT EXISTS. Реальный кейс: анти-джойн «клиенты без заказов» вернул 0 вместо 8 000.

🔗 INNER JOIN теряет строки

INNER JOIN users ↔ orders выбросит пользователей без заказов. Для «всех + их заказы» нужен LEFT JOIN. Реальный кейс: retention считали по INNER JOIN — «выжившие» дали завышенный retention в 2 раза.

⚠️ Как проверить потерю строк после JOIN

Сверьте COUNT до и после. Меньше — потеряли пользователей без связанных записей. Больше — fan-out. Оба случая искажают метрику.

✅ Блок 4. Качество данных: шесть обязательных проверок
1. Пропуски 🕳️

3% заказов без user_id → не попадают в retention.

2. Дубли 👥

0,5% дублей order_id → выручка +0,5%.

3. Типы и значения 🔢

amount = −500 (возвраты вперемешку с продажами).

4. Свежесть ⏱️

Данные отстают на 2 дня → «падение» в конце графика.

5. Сходимость ⚖️

Сайт 12,4 млн ₽ vs бухгалтерия 11,8 млн ₽.

6. Аномалии 📈

Один заказ на 10 млн ₽ поднял средний чек на 40%.

-- Экспресс-аудит таблицы orders
SELECT COUNT(*)                                   AS rows_total,
       COUNT(DISTINCT order_id)                  AS orders_unique,
       SUM(CASE WHEN user_id IS NULL THEN 1 ELSE 0 END) AS null_users,
       MIN(amount) AS min_amount, MAX(amount) AS max_amount,
       MAX(created_at)                           AS last_record
FROM orders;

-- Orphan-проверка: заказы без пользователей
SELECT COUNT(*) AS orders_without_user
FROM orders o
LEFT JOIN users u ON u.user_id = o.user_id
WHERE u.user_id IS NULL;
⚠️ Правило

Сначала проверки, потом выводы. Красивый график на грязных данных — это уверенное движение в неправильную сторону.

🩹 Блок 4а. Пропуски и выбросы: что делать, а не только найти
🗑️ Удалить строки

Когда пропусков < 5% и они случайны. Риск: если пропуски не случайны (VIP не заполняют профиль), выборка сместится.

📊 Заполнить медианой

Для числовых с выбросами. Риск: занижает дисперсию, «размывает» различия.

🔤 Заполнить модой / «unknown»

Для категориальных. Явная категория «не указано» честнее подстановки. Риск: если «не указано» > 30%, признак бесполезен.

🚩 Флаг is_null

Когда сам факт пропуска — сигнал (нет телефона → ниже конверсия). Плюс: сохраняете информацию. Минус: усложняет модель.

✅ Реальный кейс с выбросом

Средний чек вырос на 40% за месяц. Аналитик сначала решил, что сработала промо-акция. Но при проверке оказалось: один B2B-клиент сделал заказ на 10 млн ₽. Если это разовая сделка — её нужно исключить из «среднего чека» или считать медиану. Если это новый сегмент — наоборот, нужно сегментировать отчёт. Выброс — это не всегда ошибка. Иногда это сигнал.

🔤 Блок 4б. Типы данных и их влияние на анализ
🔢 Числовые

Выручка, возраст, количество. Можно среднее, медиану, сумму. Среднее — только для числовых!

🏷️ Категориальные

Город, канал, статус. Среднее бессмысленно — считайте доли и моду. «Средний город» не существует.

📊 Порядковые

Оценка 1–5, уровень «новичок/про/эксперт». Можно медиану, но не среднее: расстояние между уровнями неравное.

📅 Даты и время

created_at, event_time. Нужны часовой пояс, формат, гранулярность. UTC vs локальное время — источник расхождений.

📝 Текст

Отзывы, комментарии. Нужна токенизация и категоризация. Нельзя считать среднее по отзывам.

🧹 Грязные категории

Москва, москва, Moscow, MSK — 4 «разных» города. Нормализация до анализа обязательна.

⚠️ Реальный кейс

В отчёте по городам Москва занимала 25%, «москва» — ещё 8%, «MSK» — 4%. Итого реальная доля Москвы — 37%, а не 25%. Менеджер принял решение о бюджете на основе неверной цифры. Решение: справочник городов + нормализация на этапе загрузки.

📐 Блок 5. Описательная статистика и EDA
Среднее (mean)

Центр, чувствителен к выбросам. 4 200 ₽.

Медиана (p50)

Типичное значение. 1 800 ₽.

p90 / p99

Хвост распределения. 9 000 ₽ / 45 000 ₽.

IQR (p75 − p25)

Разброс без выбросов. 3 200 − 900 = 2 300 ₽.

✅ Реальный кейс (числа условны)

Среднее 4 200 ₽, медиана 1 800 ₽. Распределение перекошено: несколько крупных заказов тянут среднее вверх. «Типичный клиент тратит 4 200 ₽» — неправда. Правильно: «половина клиентов тратит менее 1 800 ₽, а 10% — более 9 000 ₽». Акция «скидка от 4 000 ₽» охватит лишь верхний сегмент — его долю нужно смотреть по p75/p90, а не брать «25%» на глаз.

🕳️ Блок 6. Шесть ловушек агрегации
📉 Среднее от средних

Канал А: 10 × 100 ₽; канал Б: 1000 × 10 ₽. Среднее средних = 55 ₽, реальное = 10,9 ₽. → Сумма / сумма (взвешенное).

🔀 Парадокс Симпсона

В каждом городе конверсия выросла, а общая упала — трафик сместился в «плохой» город. → Смотреть разрезы и веса.

🪦 Survivorship bias

LTV только по оставшимся клиентам завышен в 1,5–2 раза. → Вся когорта, включая ушедших.

➗ Не тот знаменатель

Retention от всех регистраций vs от активированных — разница в 3 раза. → Фиксировать определение метрики.

🔗 Дубли после JOIN

orders × order_items → выручка ×3. → Агрегировать до JOIN.

📅 Смешение периодов

Неполный месяц сравниваем с полным → «обвал −30%». → Сопоставимые окна, YoY.

💸 Блок 6а. Стоимость ошибки: ложноположительный vs ложноотрицательный
🔴 Ложноположительный (FP, ошибка I рода)

Мы решили, что эффект есть, а его нет. Пример: промо «работает» — запускаем на всю страну, тратим 5 млн ₽, а рост был сезонным. Цена: прямые потери бюджета + репутация.

🟡 Ложноотрицательный (FN, ошибка II рода)

Мы решили, что эффекта нет, а он есть. Пример: новая механика оплаты реально повышает конверсию на 3%, но мы не заметили из-за шума и откатили. Цена: упущенная выгода.

✅ Правило

В кредитном скоринге дороже FN (одобрили плохого клиента). В антифроде — FP (заблокировали честного). В маркетинге — FP (потратили бюджет впустую). В брендовых кампаниях FN (не заметили рост узнаваемости) может стоить дороже. Всегда спрашивайте: какая ошибка дороже именно в этой задаче?

🔗 Блок 7. Корреляция, причинность и статистическая база
📈 Корреляция Пирсона

Линейная связь, −1…+1. Пример: расход на рекламу и выручка, r = 0,85.

🪜 Корреляция Спирмена

Связь по рангам, устойчива к выбросам и нелинейности.

📏 Доверительный интервал

«Конверсия 5,0% ± 0,4 п.п. при 95%» — честнее одной цифры.

🎲 p-value

Вероятность наблюдать столь же или более экстремальный результат при условии, что нулевая гипотеза верна. Порог 0,05. Не «вероятность, что эффект случайный».

⚠️ Корреляция ≠ причинность

Продажи мороженого и случаи утопления коррелируют (r ≈ 0,8). Причина — лето, а не мороженое. Реальный кейс: аналитик обнаружил корреляцию 0,9 между рассылками и выручкой и предложил увеличить рассылки в 3 раза. На самом деле рассылки отправлялись в дни распродаж — причина была в скидках, а не в письмах.

📅 Блок 7а. Когорты и сезонность
👥 Когорта — группа с общим стартом

Когорта по месяцу первой покупки. Пример: средний retention по всем — 30%. Но по когортам: январь — 40%, февраль — 35%, март — 28%, апрель — 22%. Среднее скрывает деградацию новых когорт. Углублённо — в лекции 24 (продуктовая аналитика).

🌦️ Сезонность — регулярные колебания

Февраль короче января на 3 дня — сравнение «месяц к месяцу» даёт ложный «обвал». Пример: выручка марта ниже февраля на 12% — но это не падение, а сезонность. Правильно: YoY (март к марту прошлого года). Углублённо — в лекции 23 (маркетинговая аналитика).

⚠️ Правило

Любую метрику смотрите в трёх разрезах: по когортам (кто пришёл когда), по времени (YoY, а не MoM), по сегментам (канал, город, платформа). Среднее по всем — почти всегда врёт.

✅ Semantic layer

Место, где определения зафиксированы в коде, а не в головах (dbt, витрины DWH, BI-модель). Один расчёт — много потребителей. Оговорка: semantic layer требует owner'а и governance — кто-то должен обновлять определения при изменении бизнес-логики. Без этого он превращается в «ещё одно место, где определения устарели». Реальный кейс: маркетинг и финансы показывали выручку с разницей 8% — маркетинг считал с доставкой, финансы без. Semantic layer решает это раз и навсегда — при наличии owner'а.

🔁 Блок 8а. Воспроизводимость и data lineage
📌 Версионирование скриптов

SQL и Python — в Git. Каждый отчёт можно воспроизвести через год. Без этого «а как вы посчитали?» остаётся без ответа.

📅 Фиксация даты среза

В отчёте указывайте «данные на 01.11.2026». Реальный кейс: отчёт за октябрь через месяц показывал другие цифры — данные догрузились.

👀 Code review запросов

Второй аналитик проверяет логику JOIN и фильтры. Ловит fan-out и потерю строк. Дешевле, чем отчёт для инвесторов с утроенной выручкой.

🧭 Data lineage

Карта: откуда взялась цифра в дашборде. Оговорка: полезен только при полном покрытии пайплайнов — иначе создаёт ложное чувство безопасности. Реальный кейс: переименовали событие — сломались 4 дашборда. Lineage показал бы это сразу.

📊 Блок 9. Визуализация: какой график для какой задачи
📈 Динамика во времени

Линия. Избегать: столбики по 60 дням.

📊 Сравнение категорий

Горизонтальные бары. Избегать: пирог на 12 сегментов.

📉 Распределение

Гистограмма, box plot. Избегать: только среднее.

🥧 Часть от целого

Stacked bar (2–4 части). Избегать: pie с 10 долями.

🪜 Воронка / шаги

Funnel, waterfall. Избегать: линия по несвязанным шагам.

🔥 Когорты

Heatmap. Избегать: таблица без цветовой шкалы.

🔵 Связь двух величин

Scatter plot. Избегать: две оси Y без пояснения.

⚠️ Три способа соврать

Обрезать ось Y, неудачный масштаб, спрятать выбросы. Часто это небрежность, а не злой умысел — но результат один: читатель делает неверный вывод.

⚖️ Блок 9а. Этика и PII в работе аналитика данных
🔒 PII в дашборде

Email, телефон, паспорт не должны попадать в общий дашборд. Пример: в отчёте случайно оказалась колонка с телефонами — её увидели 200 сотрудников. Решение: маскирование на уровне витрины.

👥 Чувствительные сегменты

Разрезы по полу, возрасту, здоровью, религии могут дискриминировать. Пример: отчёт «конверсия по национальности» — даже без злого умысла создаёт риск. Решение: не строить такие разрезы без бизнес-обоснования.

🎯 Дискриминация в анализе

Аналитик может усилить предвзятость, выбрав неверный знаменатель. Пример: «женщины реже возвращаются» — а на самом деле среди них больше новых клиентов. Решение: контролировать когорту и стаж.

✅ Правило + правовые нормы

GDPR (ЕС), 152-ФЗ (РФ), принцип минимизации данных: собирайте и показывайте только то, что нужно для задачи. Маскирование на уровне витрины — это не только best practice, но и требование закона. Те же принципы, что в лекции 21 для ML-моделей (справедливость, прозрачность, подотчётность, конфиденциальность, безопасность), применимы и к отчётам. Не навреди.

🎯 Блок 10. Сквозной кейс: «выручка упала на 12%» (упрощённо)
1. Вопрос

«Выручка за март ниже февраля на 12%. Что случилось?» — CEO просит разобраться за 2 дня.

2. Качество данных

Свежесть: март полный. Дубли: 0,1% — не влияет. Сходимость с бухгалтерией: 0,3% — ок. Пропуски user_id: 2% — не критично. Данные чистые, падение реальное.

3. Разрезы

Каналы: органика −5%, платный −25%, email −3%. Города: Москва −8%, регионы −14%. Когорты: новые −20%, старые −4%. Гипотеза: платный трафик + новые клиенты.

4. Проверка гипотезы

Платный трафик: ставки +30% (аукцион), CPL вырос. Новые: конверсия визита в покупку упала с 3,2% до 2,4%. Причина: дорогой трафик + падение конверсии лендинга.

5. Сезонность

YoY: март 2026 vs март 2025 — −3%, а не −12%. Часть падения — сезонность (февраль был аномально высоким из-за распродажи). Реальное падение — 3%.

6. Рекомендация

1) Пересмотреть ставки (целевой CPL — вернуть к январю). 2) A/B-тест нового лендинга. 3) В отчётах использовать YoY, а не MoM. Как проверить: через 2 недели CPL и конверсия должны вернуться к baseline.

⚠️ Оговорка

Числа кейса иллюстративны: февраль = 10,8 / 0,88 ≈ 12,27 млн ₽; «9 п.п. сезонности» — это утверждение, которое в реальности нужно обосновать (например, «в прошлом году февраль тоже был на 9% выше марта из-за распродажи»); разрезы по каналам/городам/когортам не сходятся с общим −12% без весов. Кейс упрощён для учебных целей.

📝 Блок 11. Структура аналитической записки: как превратить анализ в решение
1. Факт

«Выручка за март — 10,8 млн ₽, на 12% ниже февраля». Только цифры, без интерпретации.

2. Интерпретация

«Падение на 9 п.п. объясняется сезонностью (февраль — распродажа). Реальное падение — 3%».

3. Гипотеза

«Основная причина — рост CPL в платном трафике на 30% и падение конверсии лендинга».

4. Рекомендация

«Пересмотреть ставки, запустить A/B-тест лендинга, перейти на YoY в отчётах».

❌ Контрпример плохой записки

«Выручка упала, потому что мы плохо работаем. Надо срочно всё менять». Здесь смешаны факт и интерпретация, нет гипотезы, нет «как проверить», нет рекомендации. CEO не может принять решение — только тревожиться.

✅ Формат «1 слайд — 1 вывод»

Каждый слайд отвечает на один вопрос. Факт отделён от интерпретации. Гипотеза помечена как гипотеза. Рекомендация содержит «как проверить». Ориентир для CEO — 3–5 слайдов. Реальный кейс: аналитик прислал 40-страничный отчёт — CEO не прочитал. Тот же анализ на 5 слайдах в формате «факт → вывод → рекомендация» — решение приняли за 15 минут.

⚠️ Главный вывод

Аналитик данных — это не «человек с SQL». Это специалист, который соединяет данные, качество, статистику и бизнес. Он знает источники и гранулярность, пишет SQL и проверяет план запроса, проводит шесть проверок качества, обрабатывает пропуски и выбросы, отличает среднее от медианы, избегает шести ловушек агрегации, понимает корреляцию и причинность, смотрит метрику в трёх разрезах (когорты, время, сегменты), фиксирует определения в semantic layer, обеспечивает воспроизводимость и lineage, выбирает правильный график, соблюдает этику и PII, и превращает анализ в записку «факт → интерпретация → гипотеза → рекомендация». Без него бизнес принимает решения на интуиции. С ним — на проверенных данных.

📌 Введение

Добрый день, коллеги. Сегодня мы начинаем разговор о классическом аналитике данных. Это самая базовая и самая универсальная роль в аналитике. Именно с неё начинают почти все, кто приходит в профессию. И именно на ней держатся все остальные специализации.

Главная мысль. Аналитик данных — это не тот, кто «выгружает цифры по запросу». Это тот, кто отвечает на три вопроса. Можно ли верить этим данным? Что в них на самом деле происходит? И какое решение из этого следует?

Данные — сырьё. SQL — добыча. Проверки качества — фильтр. Статистика — измерительный прибор. Машинное обучение — телескоп. Рекомендация — результат. Сегодня мы пройдём весь этот путь — от сырых данных к проверенному выводу.

📌 Блок 1. Кто такой аналитик данных

На схеме слева — таблица ролей. Аналитик данных отвечает на вопрос «что произошло, можно ли верить данным, что делать?». Продуктовый — «почему пользователи ведут себя так?». Маркетинговый — «какие каналы приносят прибыль?». Data Engineer — «как доставить данные надёжно?». Data Scientist — «что предсказать?». BI-аналитик — «как показать всем одну картину?».

Аналитик данных — универсальная база. Без SQL, проверок качества и статистики любая специализация превращается в пересказ чужих отчётов.

Живой пример

Компания хочет понять, почему упала выручка. Аналитик данных берёт данные о продажах, проверяет качество, строит разрезы по каналам, городам, продуктам, находит причину и предлагает решение. Это и есть работа аналитика данных.

📌 Конвейер

На схеме слева — пять шагов: вопрос бизнеса → данные → проверка качества → анализ → вывод и рекомендация. Это не формальность, а порядок, который защищает от ошибок. Пропустили проверку качества — получили красивый график на грязных данных. Пропустили вопрос — считали не то, что нужно.

📌 Блок 2. Источники данных и событийная модель

На схеме слева — пять базовых таблиц. users — одна строка = один пользователь. events — одно событие. orders — один заказ. order_items — одна позиция заказа. ad_costs — канал × день.

Ключевое понятие — гранулярность: что описывает одна строка. Смешение гранулярностей при JOIN — главный источник ошибок.

⚠️ Fan-out

В orders один заказ — одна строка. В order_items один заказ может занимать 3 строки. Прямое соединение утраивает сумму выручки. Реальный случай: менеджер увидел 36 млн ₽ вместо 12 млн ₽ и готовил отчёт для инвесторов. Сначала агрегируйте order_items до уровня заказа, потом соединяйте.

✅ Tracking plan

Документ, где зафиксировано, какое событие как называется, когда отправляется, какие параметры несёт. Без него purchase, order_paid, success_payment — три «разных» события об одном факте. Реальный случай: после ребрендинга переименовали событие — дашборд конверсии две недели показывал −40%.

📌 Блок 3. SQL: фундамент аналитика данных

В таблице слева — пять инструментов и типовых ошибок. GROUP BY + агрегаты — свернуть строки в метрику; ошибка — среднее от средних. JOIN — соединить сущности; ошибка — fan-out. COUNT(DISTINCT) — уникальные; ошибка — COUNT(*). Оконные функции — retention, накопительные суммы; ошибка — путать ROW_NUMBER и RANK. CTE — читаемость; ошибка — один нечитаемый запрос на 200 строк.

Пример с retention: CTE находит первую покупку каждого пользователя, LEFT JOIN и оконная функция считают, сколько вернулось в следующем месяце. Классический паттерн.

⚠️ EXPLAIN

Перед тяжёлым запросом посмотрите EXPLAIN. Он покажет, читает ли запрос все партиции, есть ли full scan, какой JOIN выбран. Без него вы не знаете, почему запрос идёт 40 минут. Сначала EXPLAIN, потом запуск.

📌 Блок 3а. NULL-семантика и JOIN-типы

Четыре скрытые ловушки SQL, на которых спотыкаются почти все новички.

NULL ≠ NULL. NULL = NULL возвращает NULL, а не TRUE. WHERE col = NULL не находит ничего. Правильно: WHERE col IS NULL. Реальный случай: фильтр «заказы без промокода» вернул 0 строк, хотя таких было 40%.

COUNT(*) vs COUNT(col). COUNT(*) считает строки, COUNT(col) — только не-NULL. Реальный случай: «10 000 клиентов» по COUNT(*), а с email — 6 200.

NOT IN с NULL. WHERE id NOT IN (SELECT id FROM t) вернёт пусто, если в подзапросе есть NULL. Используйте NOT EXISTS. Реальный случай: анти-джойн «клиенты без заказов» вернул 0 вместо 8 000.

INNER JOIN теряет строки. Пользователи без заказов молча исчезают. Для «всех + их заказы» нужен LEFT JOIN. Реальный случай: retention считали по INNER JOIN — «выжившие» дали завышенный retention в 2 раза.

⚠️ Как проверить потерю строк

Сверьте COUNT до и после JOIN. Меньше — потеряли пользователей без связанных записей. Больше — fan-out. Оба случая искажают метрику.

📌 Блок 4. Качество данных: шесть обязательных проверок

На схеме слева — шесть проверок. Разберём каждую.

1. Пропуски. Доля NULL в ключевых полях. Если 3% заказов без user_id — они не попадут в retention, метрика исказится.

2. Дубли. Сравните COUNT(*) и COUNT(DISTINCT order_id). 0,5% дублей → выручка +0,5%.

3. Типы и значения. amount = −500 — возвраты вперемешку с продажами. Числовые поля должны быть числами, даты — датами.

4. Свежесть. MAX(created_at) — когда последняя запись. Данные отстают на 2 дня → «падение» в конце графика.

5. Сходимость. Сайт 12,4 млн ₽ vs бухгалтерия 11,8 млн ₽. Расхождение 5% — сигнал, что где-то потеряны возвраты или не оплаченные заказы.

6. Аномалии. Один заказ на 10 млн ₽ поднял средний чек на 40%. Проверяйте min/max и выбросы.

В примере кода — экспресс-аудит одной таблицы. И отдельно — orphan-проверка: заказы без пользователей через LEFT JOIN ... WHERE u.user_id IS NULL. Это ловит потерю связей, о которой мы говорили в блоке 3а.

⚠️ Правило

Сначала проверки, потом выводы. Красивый график на грязных данных — это уверенное движение в неправильную сторону.

📌 Блок 4а. Пропуски и выбросы: что делать

На схеме слева — четыре стратегии. Удалить строки — когда пропусков < 5% и они случайны; риск — если пропуски не случайны (VIP не заполняют профиль), выборка сместится. Заполнить медианой — для числовых с выбросами; риск — занижает дисперсию. Заполнить модой / «unknown» — для категориальных; явная категория «не указано» честнее подстановки; риск — если «не указано» > 30%, признак бесполезен. Флаг is_null — когда сам факт пропуска сигнал (нет телефона → ниже конверсия); плюс — сохраняете информацию, минус — усложняет модель.

✅ Реальный кейс с выбросом

Средний чек вырос на 40% за месяц. Аналитик сначала решил, что сработала промо-акция. Но при проверке оказалось: один B2B-клиент сделал заказ на 10 млн ₽. Если это разовая сделка — исключить из «среднего чека» или считать медиану. Если новый сегмент — сегментировать отчёт. Выброс — это не всегда ошибка. Иногда это сигнал.

📌 Блок 4б. Типы данных

На схеме слева — шесть типов. Числовые — среднее, медиана, сумма; среднее только для числовых. Категориальные — доли и мода; «средний город» не существует. Порядковые — медиана, но не среднее: расстояние между уровнями неравное. Даты — часовой пояс, формат, гранулярность; UTC vs локальное — источник расхождений. Текст — токенизация, категоризация; нельзя считать среднее по отзывам. Грязные категории — Москва, москва, Moscow, MSK — четыре «разных» города; нормализация обязательна.

⚠️ Реальный кейс

В отчёте по городам Москва занимала 25%, «москва» — ещё 8%, «MSK» — 4%. Итого реальная доля Москвы — 37%, а не 25%. Менеджер принял решение о бюджете на основе неверной цифры. Решение: справочник городов + нормализация на этапе загрузки.

📌 Блок 5. Описательная статистика и EDA

На графике слева — распределение чека с длинным хвостом. Среднее 4 200 ₽, медиана 1 800 ₽, p90 = 9 000 ₽. Среднее чувствительно к выбросам, медиана — типичное значение, p90/p99 — хвост, IQR (p75 − p25) — разброс без выбросов.

✅ Реальный кейс (числа условны)

Среднее 4 200 ₽, медиана 1 800 ₽. Распределение перекошено: несколько крупных заказов тянут среднее вверх. «Типичный клиент тратит 4 200 ₽» — неправда. Правильно: «половина клиентов тратит менее 1 800 ₽, а 10% — более 9 000 ₽». Акция «скидка от 4 000 ₽» охватит лишь верхний сегмент — его долю нужно смотреть по p75/p90, а не брать «25%» на глаз.

EDA по шагам

1) Размер, типы, пропуски. 2) Распределения (гистограмма, квантили). 3) Выбросы (p25 − 1,5·IQR; p75 + 1,5·IQR). 4) Разрезы (канал, город, платформа). 5) Связи (корреляции без причинности).

📌 Блок 6. Шесть ловушек агрегации

На схеме слева — шесть ловушек. Среднее от средних — канал А: 10 × 100 ₽; канал Б: 1000 × 10 ₽; среднее средних 55 ₽, реальное 10,9 ₽; правильно — сумма / сумма. Парадокс Симпсона — в каждом городе конверсия выросла, а общая упала; смотреть разрезы и веса. Survivorship bias — LTV только по оставшимся завышен в 1,5–2 раза; вся когорта, включая ушедших. Не тот знаменатель — retention от всех регистраций vs от активированных, разница в 3 раза; фиксировать определение. Дубли после JOIN — orders × order_items → выручка ×3; агрегировать до JOIN. Смешение периодов — неполный месяц vs полный → «обвал −30%»; сопоставимые окна, YoY.

📌 Блок 6а. Стоимость ошибки: FP vs FN

На схеме слева — две карточки. Ложноположительный (FP, ошибка I рода) — решили, что эффект есть, а его нет. Пример: промо «работает» — запускаем на всю страну, тратим 5 млн ₽, а рост был сезонным. Цена — прямые потери бюджета + репутация. Ложноотрицательный (FN, ошибка II рода) — решили, что эффекта нет, а он есть. Пример: новая механика оплаты реально повышает конверсию на 3%, но мы не заметили из-за шума и откатили. Цена — упущенная выгода.

✅ Правило

В кредитном скоринге дороже FN (одобрили плохого клиента). В антифроде — FP (заблокировали честного). В маркетинге — FP (потратили бюджет впустую). В брендовых кампаниях FN (не заметили рост узнаваемости) может стоить дороже. Всегда спрашивайте: какая ошибка дороже именно в этой задаче?

📌 Блок 7. Корреляция, причинность и статистическая база

На схеме слева — четыре карточки. Корреляция Пирсона — линейная связь, −1…+1. Корреляция Спирмена — по рангам, устойчива к выбросам и нелинейности. Доверительный интервал — «конверсия 5,0% ± 0,4 п.п. при 95%» — честнее одной цифры. p-value — вероятность наблюдать столь же или более экстремальный результат при условии, что нулевая гипотеза верна. Порог 0,05. Это не «вероятность, что эффект случайный» — классическая, но неверная интерпретация.

⚠️ Корреляция ≠ причинность

Продажи мороженого и случаи утопления коррелируют (r ≈ 0,8). Причина — лето, а не мороженое. Реальный кейс: аналитик обнаружил корреляцию 0,9 между рассылками и выручкой и предложил увеличить рассылки в 3 раза. На самом деле рассылки отправлялись в дни распродаж — причина была в скидках, а не в письмах.

На второй схеме — иерархия доказательств: A/B → квази-эксперимент (DiD, IV, RDD) → регрессия с контролем → корреляция. Оговорки: DiD требует предпосылки parallel trends; IV и RDD — тоже квази-экспериментальные методы, в экономике часто сильнее обычной регрессии; регрессия выше корреляции только при правильном выборе контролей — если контролировать collider, можно получить смещение. Детали A/B-тестов (MDE, SRM, peeking) — в лекции 24 (продуктовая аналитика).

📌 Блок 7а. Когорты и сезонность

На схеме слева — две карточки. Когорта — группа с общим стартом. Пример: средний retention по всем — 30%, но по когортам: январь — 40%, февраль — 35%, март — 28%, апрель — 22%. Среднее скрывает деградацию новых когорт. Углублённо — в лекции 24 (продуктовая аналитика).

Сезонность — регулярные колебания. Февраль короче января на 3 дня — сравнение «месяц к месяцу» даёт ложный «обвал». Пример: выручка марта ниже февраля на 12% — но это не падение, а сезонность. Правильно: YoY (март к марту прошлого года). Углублённо — в лекции 23 (маркетинговая аналитика).

⚠️ Правило

Любую метрику смотрите в трёх разрезах: по когортам (кто пришёл когда), по времени (YoY, а не MoM), по сегментам (канал, город, платформа). Среднее по всем — почти всегда врёт.

📌 Блок 8. Слой метрик: одна версия правды

В таблице слева — четыре метрики и их спорные определения. Выручка: с НДС? с возвратами? с доставкой? Зафиксировано: оплаченные заказы минус возвраты, без доставки. Активный пользователь: зашёл или совершил действие? Зафиксировано: ≥1 целевое действие за 30 дней. Новый клиент: первая регистрация или первый заказ? Зафиксировано: первый оплаченный заказ. Период: UTC или локальное? Зафиксировано: единый часовой пояс отчётности.

✅ Semantic layer

Место, где определения зафиксированы в коде, а не в головах (dbt, витрины DWH, BI-модель). Один расчёт — много потребителей. Оговорка: semantic layer требует owner'а и governance — кто-то должен обновлять определения при изменении бизнес-логики. Без этого он превращается в «ещё одно место, где определения устарели». Реальный кейс: маркетинг и финансы показывали выручку с разницей 8% — маркетинг считал с доставкой, финансы без. Semantic layer решает это раз и навсегда — при наличии owner'а.

📌 Блок 8а. Воспроизводимость и data lineage

На схеме слева — четыре карточки. Версионирование скриптов — SQL и Python в Git; каждый отчёт можно воспроизвести через год. Фиксация даты среза — «данные на 01.11.2026»; реальный кейс: отчёт за октябрь через месяц показывал другие цифры — данные догрузились. Code review запросов — второй аналитик проверяет логику JOIN и фильтры; ловит fan-out и потерю строк. Data lineage — карта, откуда взялась цифра в дашборде.

⚠️ Оговорка про lineage

Lineage полезен только при полном покрытии пайплайнов — иначе создаёт ложное чувство безопасности. В реальности кто-то строит отчёт в Excel, кто-то в BI, кто-то в блокноте. Реальный кейс: переименовали событие — сломались 4 дашборда. Lineage показал бы это сразу — если бы покрывал все пайплайны.

📌 Блок 9. Визуализация

На схеме слева — восемь карточек. Динамика во времени — линия; избегать столбиков по 60 дням. Сравнение категорий — горизонтальные бары; избегать пирога на 12 сегментов. Распределение — гистограмма, box plot; избегать только среднего. Часть от целого — stacked bar (2–4 части); избегать pie с 10 долями. Воронка / шаги — funnel, waterfall; избегать линии по несвязанным шагам. Когорты — heatmap; избегать таблицы без цветовой шкалы. Связь двух величин — scatter plot; избегать двух осей Y без пояснения. Три способа соврать — обрезать ось Y, неудачный масштаб, спрятать выбросы.

⚠️ Про «три способа соврать»

Это классика (How to Lie with Statistics, Huff). Но часто это не злой умысел, а небрежность — и результат один: читатель делает неверный вывод. В лекции, где есть блок 9а про этику, стоит помнить: визуализация — это тоже этический выбор.

📌 Блок 9а. Этика и PII

На схеме слева — три карточки. PII в дашборде — email, телефон, паспорт не должны попадать в общий дашборд. Пример: в отчёте случайно оказалась колонка с телефонами — её увидели 200 сотрудников. Решение: маскирование на уровне витрины. Чувствительные сегменты — разрезы по полу, возрасту, здоровью, религии могут дискриминировать. Пример: отчёт «конверсия по национальности» — даже без злого умысла создаёт риск. Решение: не строить такие разрезы без бизнес-обоснования. Дискриминация в анализе — аналитик может усилить предвзятость, выбрав неверный знаменатель. Пример: «женщины реже возвращаются» — а на самом деле среди них больше новых клиентов. Решение: контролировать когорту и стаж.

✅ Правило + правовые нормы

GDPR (ЕС), 152-ФЗ (РФ), принцип минимизации данных: собирайте и показывайте только то, что нужно для задачи. Маскирование на уровне витрины — это не только best practice, но и требование закона. Те же принципы, что в лекции 21 для ML-моделей (справедливость, прозрачность, подотчётность, конфиденциальность, безопасность), применимы и к отчётам. Не навреди.

📌 Блок 10. Сквозной кейс: «выручка упала на 12%»

На схеме слева — шесть шагов. 1. Вопрос: «Выручка за март ниже февраля на 12%. Что случилось?» — CEO просит разобраться за 2 дня.

2. Качество данных: свежесть — март полный; дубли — 0,1%, не влияет; сходимость с бухгалтерией — 0,3%, ок; пропуски user_id — 2%, не критично. Данные чистые, падение реальное.

3. Разрезы: каналы — органика −5%, платный −25%, email −3%; города — Москва −8%, регионы −14%; когорты — новые −20%, старые −4%. Гипотеза: платный трафик + новые клиенты.

4. Проверка гипотезы: платный трафик — ставки +30% (аукцион), CPL вырос; новые — конверсия визита в покупку упала с 3,2% до 2,4%. Причина: дорогой трафик + падение конверсии лендинга.

5. Сезонность: YoY — март 2026 vs март 2025 — −3%, а не −12%. Часть падения — сезонность (февраль был аномально высоким из-за распродажи). Реальное падение — 3%.

6. Рекомендация: 1) Пересмотреть ставки (целевой CPL — вернуть к январю). 2) A/B-тест нового лендинга. 3) В отчётах использовать YoY, а не MoM. Как проверить: через 2 недели CPL и конверсия должны вернуться к baseline.

⚠️ Оговорка

Числа кейса иллюстративны: февраль = 10,8 / 0,88 ≈ 12,27 млн ₽; «9 п.п. сезонности» — это утверждение, которое в реальности нужно обосновать (например, «в прошлом году февраль тоже был на 9% выше марта из-за распродажи»); разрезы по каналам/городам/когортам не сходятся с общим −12% без весов. Кейс упрощён для учебных целей.

📌 Блок 11. Структура аналитической записки

На схеме слева — четыре блока. 1. Факт — «выручка за март — 10,8 млн ₽, на 12% ниже февраля»; только цифры, без интерпретации. 2. Интерпретация — «падение на 9 п.п. объясняется сезонностью (февраль — распродажа); реальное падение — 3%». 3. Гипотеза — «основная причина — рост CPL в платном трафике на 30% и падение конверсии лендинга». 4. Рекомендация — «пересмотреть ставки, запустить A/B-тест лендинга, перейти на YoY в отчётах».

❌ Контрпример плохой записки

«Выручка упала, потому что мы плохо работаем. Надо срочно всё менять». Здесь смешаны факт и интерпретация, нет гипотезы, нет «как проверить», нет рекомендации. CEO не может принять решение — только тревожиться.

✅ Формат «1 слайд — 1 вывод»

Каждый слайд отвечает на один вопрос. Факт отделён от интерпретации. Гипотеза помечена как гипотеза. Рекомендация содержит «как проверить». Ориентир для CEO — 3–5 слайдов. Реальный кейс: аналитик прислал 40-страничный отчёт — CEO не прочитал. Тот же анализ на 5 слайдах в формате «факт → вывод → рекомендация» — решение приняли за 15 минут.

📌 Заключение

Мы разобрали роль аналитика данных, источники и событийную модель, SQL, качество данных (шесть проверок), пропуски и выбросы, типы данных, описательную статистику и EDA, шесть ловушек агрегации, FP/FN, корреляцию и причинность, когорты и сезонность, слой метрик, воспроизводимость и lineage, визуализацию, этику и PII, сквозной кейс «−12%» и структуру записки.

Главный вывод: аналитик данных — это не «человек с SQL». Это специалист, который соединяет данные, качество, статистику и бизнес. Без него бизнес принимает решения на интуиции. С ним — на проверенных данных.
